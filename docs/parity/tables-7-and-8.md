## Facts about the Rust port that affect both tables (verified)

- There is NO per-table delegate layer at all. `TableDef.delegate` is parsed (DEF `delegate: Option<String>`) but never read. Table logic that exists today is either generic element behaviour in `PhysicsWorld::step` or hard-coded by element id (`LaunchBarrier*`, `TriangleWall*`, `BallSaver-*`, `saver_for_drop_bank`). No callbacks exist for gameStarted, ballLost, tick, processCollision, allDropTargetsInGroupHit, allRolloversInGroupActivated, ballInSensorRange, spinnerActivated.
- Single ball only: `PhysicsWorld.ball_handle: Option<RigidBodyHandle>` (PW L403 region), `remove_ball`/`park_ball` (PW L1677, L1696). No ball list, no create/remove of extra balls.
- No game messages: `GameState` (GS) has score, high_score, balls_remaining, phase, multiplier, super_mode_ticks only; DMD (`src/ui/dmd.rs`) has no message line.
- No scheduled actions (the only timers are tick counters / `reset_timer` for drop banks).
- Scoring: `GameState::add_score` multiplies by an integer multiplier (GS L55); `physics.score_events: Vec<u64>` carries raw points. No score animation at a position.
- Sensors: only `LaunchBarrierSensor`, `LaunchBarrierRetract` (by id) and sensors with `ballLayer` (layer switches, PW L575-585, L1489-1513) are used. Sensors are not addressable by id otherwise; there is no "most recent sensor id" per ball.
- Layers: the original gives every layer its own Box2D world, so an element with no `"layer"` (layer 0) only touches a ball on layer 0. The Rust port instead treats an element with no layer as universal (PW L379-390 comment, `add_wall` L741) and only walls/arcs/paths carry a layer; bumpers, flippers, rollover groups, drop targets, kick walls and sensors have NO layer field in DEF (BumperDef, FlipperDef, RolloverGroupDef, DropTargetGroupDef, SensorDef). Negative layers are mapped to an inert layer 31 (DEF L86-95) so they never collide and are never drawn.
- Renderer (REN L95-135) draws walls with `layer == None` always, a layer wall only when it equals the ball's current layer, and skips every other layer entirely (the original draws other layers faintly with `inactiveLayerColor`, which is parsed in DEF for arcs/paths but unused). Layer colours are a fixed 4 entry table (`COL_LAYER`, index `min(n,3)`), so layer 4 reuses layer 3's colour.
- Rollover groups (PW L1352-1418) differ from the original: they auto-flash and auto-reset on completion, and award `group.score` as an extra completion bonus (original: no completion bonus, no auto reset; the delegate decides). They also ignore layers, have no `setVisible`, no "activate first unactivated", no set-all, no per-index set, no `ignoreBall` toggle at runtime.
- Drop target groups: DEF `DropTargetGroupDef` ONLY reads explicit `positions` (DEF L482-497). The `wallStart`/`wallEnd`/`numTargets`/`gapFromWall`/`startDistanceAlongWall`/`targetWidth`/`gapBetweenTargets` generator (original `elements/DropTargetGroupElement.java` L63-93) is NOT implemented (grep for `wallStart` in `src/` finds nothing). Result: in the shipped Rust `assets/tables/table7.json` and `table8.json` every drop-target group except table 8 `InlineTargets` is built with ZERO targets (`build_drop_target_group`, PW L942). Table 7: `DropTargetLeftSave`, `DropTargetRightSave`, `MiniFieldLeftTargets`, `MiniFieldTopTargets`. Table 8: `SpecialTarget`, `RightBankTargets`, `EightBallTarget`. Also the same gap hits tables 3, 4, 5, 6. This is the single biggest blocker for both tables.
- WallDef/WallArcDef/WallPathDef have no `ignoreBall` field (only RolloverGroupDef has it). Walls and paths marked `ignoreBall` in the JSON therefore become SOLID colliders in Rust (see per-table notes).
- `WallElement` `disabled` is honoured only by skipping the wall entirely (PW L728), except for the id `LaunchBarrier`. There is no generic `setRetracted`/show/hide for walls other than: `retractWhenHit` kick walls + `restore_ball_saver` (PW L1540), the launch barrier, and table 5 moving walls.
- Rust table JSONs are identical to the originals except `ballradius` (table 7: 0.46 vs original 0.49; table 8 unchanged). Table 8 ball radius 0.4, gravity 4.5; table 7 gravity 4.

### Star field projection (precise)

Catalogue and projection space
- Each star is a unit vector `(x, y, z) = (cos dec cos ra, -cos dec sin ra, sin dec)`.
- View target `(RA, Dec, angularRadius)` lives in `starState.currentTarget`. Per tick: `x1 = x cosRA - y sinRA`, `y1 = x sinRA + y cosRA`, `z1 = z`; then `x2 = x1 cosDec + z1 sinDec`, `y2 = y1`, `z2 = -x1 sinDec + z1 cosDec`. The look direction ends at (1,0,0). A star is visible if `x2 > 0` and `y2^2 + z2^2 < angularRadius^2`. The projected 2D point is `(y2, z2)` (orthographic; screen x = y2, screen y = z2, y up). Because the catalogue uses `-sin ra`, east (larger RA) lands on the left like a real sky map.
- Projection arrays are sized to the whole catalogue (about 1,500 entries) and rebuilt every tick (`projection.clear()` then `add(...)` per visible star) with `starIndexToProjIndex` for O(1) lookup (-1 = not projected).

Mapping to field coordinates (`shapesFromProjection`, F7 L602-648)
- Centre = `StarViewBoundary` rollover 0 centre (9.4, 13); radius = its radius (5). `distScale = starViewRadius / currentTarget.angularRadius`; a star draws at `centre + (projX, projY) * distScale`.
- Star circle: `baseRadius = starViewRadius * 0.015` (0.075 field units); `rmul = 1.5` if magnitude <= 0, `0.75` if magnitude >= 4, else 1.0. Alpha = 255 for magnitude <= 0, else `max(0, 255 - 30*mag)`. SOLID filled `Shape.Circle`.
- Colours (RGB, with the alpha above): active star in current constellation yellow (240,240,0); not-yet-active star in current constellation green (0,240,0); active star in a different constellation dim yellow (192,192,0); everything else white (240,240,240).
- Order: all circle shapes are built in projection order (catalogue is brightness sorted) and then reversed so brighter stars draw last (on top).
- Lines: for every constellation, for each activated star and each segment endpoint that is also activated and projected, a `Shape.Line` (colour 240,240,240 alpha 192) joins them. These come after the circles. So only completed pairs of activated stars draw lines, in any constellation (also locked ones, as long as in view).
- Shapes are pushed with `field.setShapes(list)` every tick; the field draws them as custom shapes at layer 0 beneath field elements (`model/Field.java` draw ordering L553-560). Shape types: `model/Shape.java` (Circle with fill type, Line).

How stars get activated and constellations get locked
- Stars: ball on layer 0 within 0.5 field units of a projected star of the CURRENT constellation (F7 L175-194). Activation score 500 each.
- A constellation counts as complete when all its star indices are activated. Not-multiball: lights the lock lane (see #10, #13); the next ball into the lock sensor goes to layer 4 and into a lock rollover (#15), which locks the constellation. In multiball, completion locks it immediately (#11). Jackpot when all 6 locked (#19).

How the view moves: see rows 5 to 8 (wandering pan, 10 s fly-to, 1.2x constellation radius, return to start).

### Dependencies summary (table 7)

Must exist before table 7 can work:
1. A per-table delegate/script layer with hooks: gameStarted, tick (with game-time delta), allRolloversInGroupActivated, allDropTargetsInGroupHit, ballInSensorRange (by sensor id, with per-ball most-recent-sensor id), and a way to run table-specific code (Rust has none).
2. Multi-ball support: ball list, create ball at (x,y) with velocity and layer, remove ball without ball loss, multiball-ended detection, multiball saver rules (original `restoreLostBallInMultiball` within `multiballSaverDuration`).
3. Scheduled actions (game-time callbacks) for the 1000/3500/6000 ms multiball release.
4. Game messages (timed text with optional sound) and a message sound; message strings (see strings.xml names in this report).
5. Score animation at a position; score multiplier +1 with message ("incrementAndDisplayScoreMultiplier").
6. Renderer support for arbitrary shapes (`setShapes`): per-shape RGBA colours, filled circles of fractional radius, lines, redrawn each frame (~100 to 300 visible stars). Rust has braille canvas helpers (`draw_line`, `fill_ellipse`, `draw_ellipse`) but `FieldSnapshot` has no shape list and terminal colours have no alpha (blend manually against the background).
